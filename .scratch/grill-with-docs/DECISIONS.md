## Structural (agreed in discussion)

- Endpoint abstraction: app talks only to an OpenAI-compatible endpoint; serving detail lives only in the serving profile.
- **Metric = vector of computed values (2026-10-08b, applies to Q15 + Q16):** a metric's per-item output is a vector of computed values; each value carries a field name + full provenance. Multi-dimensional interpretability and presentation of that vector — composites, cross-quality confound exposure, how to "read" it — are out of scope. The one preserved special case is the multi-valued judge result: values sharing single-call provenance, correlated (a recorded property, not an interpretive one). This subsumes the "one score, one quality" interpretive discipline.
- **Judge / model-under-test server separation (user directive, 2026-10-08)**: the app-owned spawn/stop lifecycle is scoped to the **model-under-test endpoint only**. The judge is addressed as a **bare endpoint profile** (base URL, model name, credential by reference) — no launch spec, no lifecycle in v1. Manifest keeps one fully recorded server lifecycle; judge identity = endpoint + model name (a hosted model name is the pin that exists for hosted services). Fail-fast: judge preflight (one trivial completion) before any scoring; judge model identifier must differ from model-under-test identifier (self-judging = misconfiguration, not a warning). Consequence: without a hosted key (Q4), judge-based metrics (conciseness rubric, instruction-following) fall out of v1 — the app will not manage a second server, and a manually-run judge would inject an unrecorded, unverified identity into results (same rationale as Q9's rejection). If a local judge is ever needed later: its own launch profile + independent lifecycle unit — a separate decision then, never a shared mechanism.
- Preflight failure classes: model doesn't fit/load, context > server n_ctx, invalid params, server death mid-run → abort with file:line context, no retries/fallbacks.
- Runs = immutable, self-describing directories (`runs/<date>_<model>/` + manifest). Clean slate = new run dir; reports render from explicitly selected runs.
- Phase 2 response cache ⇒ server only needed during the generation phase (and is app-stopped after it).
- Model download is a human step; the app verifies the model file exists before spawning. (The file-content sha256 pin was removed from the config 2026-10-13 as a dependent value — a file swapped at the same path is NOT detected; accepted cost of the label-based model identity, content-hash pin = deferred upgrade.)

- **Q3 (SETTLED 2026-10-08, scope cut)**: The **specific choice of corpora is outside the scope of the software architecture.** The architecture is corpus-agnostic: it consumes the canonical form (Q13) and validates against configurable bounds (e.g., the ~8–12k transcript-token length window); which corpus, how many items, and the stratification criteria are **curation-time data decisions**, made and documented at Phase 1 data work, not in the architecture. Working plan (curation-side, not an architectural commitment): MeetingBank first, QMSum fallback.

## Session 2026-10-18 — Q17f1 ACCEPTED — atomic units: what one transaction contains

## Session 2026-10-18 — Q17f2 ACCEPTED — complete-or-absent visibility

Carries the Q11'' commit contract (line 45: "a record is durably written, complete-or-absent to any reader") over to the current store design, now that the transaction discipline of Q17f1 exists.

- Every record any reader can see in the store is complete: a committed generations row has all its keys resolvable (to transcripts/models/prompt_templates rows), and a committed evaluation row has all its keys resolvable (to its generations row, and to a reference_summaries row whenever its reference hash is present). Q17f1's same-transaction discipline guarantees this at commit time.
- No intermediate state is recorded anywhere: no pending flags, no "in progress" markers, no partial or staging rows. A unit is either fully committed or absent entirely.
- Practical consequence: any store-reading command (score/sweep pre-scan, report, check) can only ever observe complete records — a later run can never skip, deduplicate against, or report on a half-written unit.
- No extra machinery owed: SQLite's transaction semantics provide this for a single process. This item makes no claim about concurrent app instances (Q17g) or disk-level durability (out of scope per Q11'' — process/OS crash only, not disk failure).
- **User refinement (recorded):** the converse of dangling references is NOT a problem — extraneous rows that are not referenced as a key by any other row, whatever the cause (e.g. transcripts or reference_summaries rows nothing points at; generations rows with no evaluation rows; judges rows never used), are tolerated. The app owes no detection, cleanup, or consistency-checking duty for them.

## Session 2026-10-18 — Q17f3 ACCEPTED — crash envelope

Carries the Q11'' durability boundary (line 45: "guarantees process/OS crash only, NOT disk failure") over to the current store design.

- **Covered:** process crash (segfault, kill -9) and OS crash (reboot, kernel panic) where the disk survives. Committed data before the crash survives; SQLite's journal/WAL replay handles the torn transaction at next open.
- **NOT covered:** disk hardware failure or filesystem corruption. No claim made; the existing safety net is human discipline (Q17e timestamp rationale: created_at/updated_at as the instrument for external fixing).
- **Loss bound:** a crash loses at most one in-flight unit — the generate item (entry × summarizer) or score unit (item, scorer) whose transaction was mid-commit. By Q17f1/Q17f2 it is simply absent (all-or-nothing) and re-runs on the next invocation (pre-scan finds nothing committed ⇒ "to run").
- **Recovery cost:** at most one model call or one judge call of rework — the same cost center as any failed unit (Q17f1). No partial record can exist that needs repairing.
- **No recovery mechanism owed:** no repair command, no journal of intent, no recovery phase. Resume = re-run the same command; the store-as-index principle (Q17f5) makes the pre-scan the entire recovery logic.
- **Store:** no shape change ⇒ no docs/store-schema.md update required.

## Session 2026-10-18 — Q17f4 ACCEPTED — never-mutated-after-commit, consolidated

Consolidates Q17c1‴ (lines 133–141), Q17d′2 (line 720), and the store-schema annotations into one store-level + command-layer statement.

- **Store-level contract:** a write whose identity already exists never changes key values or stored result content. The ONLY post-commit writes the app performs anywhere are: (1) the `updated_at` stamp — overwritten iff a committing upsert targets an existing identity AND the observed non-key values differ (line 136; identical re-sighting = no-op, no stamp); (2) updating the non-key courtesy columns to last-seen values in that same UPDATE — `transcripts`/`reference_summaries`: `dataset_name`/`entry_id`/`entry_index`; `models`: `name`/`model_path`; `judges`: `name`/`endpoint`/`api_key_env`.

## Session 2026-10-18 — Q17g ACCEPTED — concurrent instances: single active instance per store; no locking machinery

Re-derived at its turn (original text never captured, flagged line 113; subject pinned by Q17f2, line 759: "no claim about concurrent app instances (Q17g)").

- **Supported mode:** at most one active app instance per store file. Concurrent multi-instance use of one store is NOT supported, and is documented as such (one line in the design doc).
- **No app-level locking machinery:** no lock file, no pid file, no retry/backoff. SQLite's built-in file locking is the only mechanism. SQLite's own guarantee covers file integrity (concurrent access cannot corrupt the store file); the app makes no guarantees about outcomes, costs, or success of an unsupported concurrent run.
- **Failures fall out of existing rulings, no new machinery:** a second writer surfaces SQLite's busy/locked error as a plain runtime error (exit 1, C2); a second spawn on the same port fails the readiness check and goes through the standard spawn-failure path (exit 1 + last ~20 lines of server log, C10).
- **No stale-lock risk:** with no lock file, the Q17f3 crash envelope is unchanged — a crashed instance leaves nothing to clean up (SQLite's lock is released with the process). An advisory lock file would have introduced a stale-lock failure mode requiring cleanup logic, contradicting Q17f3/Q17f5 (re-run = entire recovery).
- **Races cost, they don't corrupt:** the pre-scan happens at command start, so two instances can double-spend a model/judge call on the same unit; the store resolves the collision per Q17f4 (first-committed content wins, a differing re-sighting only stamps `updated_at`). Worst case = wasted calls, never inconsistent data.
- **Revisit trigger:** first real need for concurrent access to one store (e.g. parallelizing work across instances) — at that point the machinery options (WAL + busy timeout, explicit locking, per-instance stores) get ruled on.
- **Store:** no shape change ⇒ no docs/store-schema.md update required.
